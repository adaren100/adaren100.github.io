**[How iFood scales coding agents across 15,000 repositories](https://openai.com/business/customer-stories/ifood)** — _OpenAI · Nov 24_

**Main takeaway:** A customer engineering story: iFood built a Remote Agents Platform that turns routine engineering chores into API calls — submit a prompt, the work runs in an isolated remote sandbox, and the result comes back as a merge request. Its first big internal consumer was the security platform, where the number of vulnerabilities fixed more than doubled.

**Main methods:**
- **The problem is scale, not difficulty.** iFood maintains more than 15,000 repositories, each periodically needing the same kinds of chores: validating code against internal standards, fixing vulnerable dependencies, running an analysis. "Solving this for one repository is easy. The challenge is solving it at scale," says Senior Software Engineer Victor Coelho.
- **What was missing was a runtime, not a use case.** Before the platform, teams each built their own fragmented solution and all hit the same wall — no shared agentic runtime or execution infrastructure to delegate to.
- **A REST API as the only entry point.** Users POST a prompt plus environment requirements to create a run; the platform manages the whole lifecycle internally and delegates execution to isolated sandboxes, with progress observable in real time.
- **Deterministic steps bookending agentic execution.** The runner starts deterministically (clone the repo, import the skills the agent is allowed to use, set up the working branch) and ends deterministically (publish the merge request, expose the generated artifacts). Only the middle is agentic, which is what makes the overall workflow predictable.
- **GPT-5.6 Luna inside the sandbox.** The agentic middle section runs GPT-5.6 Luna; the post has a dedicated section on why that model was chosen and another on how the platform judges whether the agent actually completed the task.
- **Asynchronous by design, and borrowed by design.** Developers fire and forget rather than babysitting runs, and the team modeled the interface on the APIs that inspired it. The post also carries a results-at-a-glance panel and a lessons-for-leaders section.

**[iFood 怎么把 coding agent 铺到 15,000 个 repo 上](https://openai.com/business/customer-stories/ifood)** — _OpenAI · 11月24日_

**Main takeaway:** 这是篇客户工程案例：iFood 自己搭了个 Remote Agents Platform，把日常工程杂活变成 API 调用，你丢个 prompt 过去，活在远端隔离 sandbox 里跑完，结果以 merge request 的形式回来。第一个大规模吃这套东西的是他们内部的安全平台，修掉的 vulnerability 数量直接翻了一倍多。

**Main methods:**
- **难的不是任务本身，是量。** iFood 手上有一万五千多个 repo，每个都要定期干同样那几件事：按内部规范校验代码、修有漏洞的依赖、跑分析。他们的 Senior Software Engineer Victor Coelho 说，"给一个 repo 解决这事很简单，难的是在规模上解决。"
- **缺的是 runtime，不是场景。** 平台之前，各个团队各搞一套，最后都撞在同一面墙上：没有一层共享的 agentic runtime，也没有能托管执行的基础设施。
- **对外只留一个 REST API。** 用户把 prompt 和环境需求提交上去创建一个 run，平台内部管完整的生命周期，执行则交给隔离的 sandbox，中途进度可以实时看。
- **agentic 那段被确定性步骤夹在中间。** runner 开头是确定性的（clone 仓库、导入 agent 能用的 skills、建好工作分支），结尾也是确定性的（发 merge request、把产物暴露出来），只有中间那段交给 agent。正是这个夹心结构让整个 workflow 变得可预期。
- **sandbox 里跑的是 GPT-5.6 Luna。** 中间这段 agentic 执行用的是 GPT-5.6 Luna，原文专门有一节讲为什么选它，还有一节讲平台怎么判断 agent 到底有没有真把任务做完。
- **异步是故意的，接口也是照着别人学的。** 开发者提交完就不用守着了，团队还特意把接口照着启发他们的那些 API 来设计。文章里另外附了一块结果汇总面板和一节写给管理者的经验。
